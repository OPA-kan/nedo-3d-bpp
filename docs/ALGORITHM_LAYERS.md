# アルゴリズム階層と、階層ごとの現在地

**Status:** Proposed（分割の提案）／ Findings（測定結果の要約）
**Date:** 2026-08-03

課題A/B/Cでbranchを分ける運用が限界に来ている。`ABC_IMPLEMENTATION_SPEC`
§1が「A/B/Cは同じ厳密配置コアを使う」と定めている以上、**タスク境界は
コードの境界と一致しない**。実際に衝突が起きている（末尾に実例）。

代わりに**アルゴリズム階層**で分ける案と、各階層で現在何が分かっているかを
まとめる。

---

## 階層

| 層 | 中身 | 効く課題 |
|---|---|---|
| **L0 計器** | fingerprint、evidence台帳、ablation harness、knob registry | 全部 |
| **L1 候補生成** | envelope、anchor generator、搬入経路、支持面定義 | A/B/C |
| **L2 選択** | `Ranker.score`、risk rerank、将来可行性proxy | A/B/C |
| **L3 配分** | 試行予算、first/deep pass、終盤の深さ | A/B/C |
| **L4 順序** | `constructive_order`、`Agent.optimize` | **Aのみ** |

`optimize` は `agent.optimize` が真のときしか呼ばれない（
`test_offline_budget_never_reaches_the_online_policy` が固定）。したがって
**L4だけが1課題にしか効かない**。L1〜L3は3課題すべてを通る。

これが分割の根拠になる。L1の改善は3倍のレバレッジを持ち、L4は1倍。

## L1 候補生成 — ここが今いちばん動いている

**envelope が箱の公式だった。** 生成器はy下限を
`-width/2 + thickness + dy/2 + clearance` と置いていたが、AKE/AKN由来の
容器のy平面は非対称で真の範囲は `[-W/2, +W/2 - thickness]`。**低y側だけ
thickness分ちょうど狭かった**。両generatorが同じ式を別々に持っていたため、
両方を網羅列挙しても帯を外し続けていた。

効果は桁が違う。「真の詰み」と認定されていた状態で、**候補0個 → 33個、
全部が物理的に安全**。公式スコアは 17.581 → 23.246 → **35.375**（倍）。
時間コストはゼロ。

**ゲート増幅が減衰している。** placed上昇に対するゲート4成分の上昇は
14x → 6.7x、pass-fraction下界は 0.207 → 0.294 → **0.532**。
**placedだけを追う戦略には期限がある**。ゲート通過後は
`E[placement|pass] ≤ 31.8`、`E[soft|pass] ≤ 40.0` に対し
`E[cog|pass] ≤ 76.4` で、placementとsoftが依然最悪の2成分。

**board featuresは「幾何的に置ける場所」を数えていて、「搬入で到達できる
場所」を数えていない。** oracleが候補0と判定した状態で site 123個を報告
（`board-receptivity-is-not-a-feasibility-predictor`）。原因は2つとも構造的:

1. site カウントが搬入経路契約を一切見ない
2. `board_occupancy` がsoft/priorityを含む全既配置をheight mapに刻む一方、
   `support_surfaces` はsoft/priorityを支持面から除外している。
   **支持面の定義が2箇所で食い違っている**

**`F[x,z]`（Y方向前方遮蔽、安い必要条件）は仕様にあるが未実装。**
あるのは候補ごとの厳密判定 `Geometry.transport_path_clear` だけで、
site カウントはこれを呼んでいない。

## L2 選択 — 3回試して3回棄却、ただし棄却の根拠が崩れた

`Ranker.score` は**係数8個の加重和**で、毎手の全決定を支配する。
`BOARD_RECEPTIVITY.md` に役割は明記されている:

> その手で**得るもの**を採点する。その手が盤面から**奪うもの**に対応する
> 項は一つもない。

**値の選定根拠だけが未記録。** `RELEASE_RISK_RERANK_LAMBDA` のように
事前登録ablationで選ばれた形跡がない。

「奪うもの」を見る方向は3回実装されて3回とも採用されていない:

| 実装 | 結果 |
|---|---|
| board receptivity（A/R/H） | MIXED、6W/3L/1T、p=0.508 |
| pool_resilience | 既定にならず |
| visible pool rollout（enforce） | 137.667 → 131.000 と悪化、棄却 |

**しかしこれらは壊れた計器の上の結果である可能性が高い**（上記123対0）。
`Rule 5.0`（未検証の計器の出力は結論ではなくdraft）がそのまま該当する。

反対方向の証拠もある。Task Cの horizon labels は
**step-18の選択が2〜4 placedの価値を持つ**と測定した。選択に余地はある。

**本当の難所はコスト。** 「次状態に残る将来可行性」を正しく評価するには
候補ごとに仮想next状態で候補生成を回す必要があり、1手8秒・
`policy_seconds` 6.52秒では入らない。安い近似は搬入契約を落とし、
正確な評価は予算に入らない。**この緊張は3回の試行のどれも解いていない。**

## L3 配分 — 唯一の採用実績があり、未着手が残っている

`ANCHOR_FIRST_PASS_ATTEMPTS` 64→256 が **placed 143→179（+25%）、
9W/0L/1T、符号検定 p=0.0039**。総試行数と最大policy時間は不変なので、
同じ仕事の再配分。**この repo で最も強い採用結果**。

**二段構えが消えている。** `ANCHOR_DEEP_PASS_ATTEMPTS` も256なので、
`attempts_per_unit` は初回も以降も同値になり、round構造が一様化した。
deep passが何のためにあったにせよ、もう区別された仕事をしていない。

**終盤の状態依存深さは未着手。**

## L4 順序（Aのみ） — 掘り尽くして空だった

このセッションの担当。**採用に至った変更はゼロ。**

### 目的関数

`OFFLINE_FILL_WEIGHT` / `OFFLINE_STABILITY_WEIGHT` は
`DryRunResult.weighted_score` にしか入らず、**呼び出し元ゼロの死んだコード**。
実際に選んでいるのは `rank_key`（辞書式5要素）で、
`fill_ratio = placed_volume / total_capacity` は分母がケース固定なので
`placed_volume` の単調変換、**タプル内で冗長**。実効キーは
`(placed_count, placed_volume)`。

### 探索

`current_items` を無条件更新しており、ADR-001 §5「採択: 辞書式評価が改善した
場合だけ更新」に**違反**。実体はbest-so-far記録付きの拡散。

**仕様どおりに直すと悪化する**（hillclimb 20.00 対 walk 22.00）。

### そして帰無モデルに負ける

60 distinct order・3seed・true envelope下:

| 提案分布 | 平均placed | 最小 |
|---|---:|---:|
| 近傍ウォーク（出荷版） | 22.00 | 20 |
| **一様ランダム** | **23.00** | **23** |
| 近傍ウォーク + volume起点 | 24.33 | 23 |

**近傍構造・受理規則・出発点という機構一式が、ランダムに引くより悪い。**
今日測った受理規則3種・multi-start・構築4種は、すべて「くじの引き方」の
比較だった。

### 構築順序

`ADR-001 §1` は3量（体積・最大底面積・質量）の複合スコアを指定しているが、
**実装は体積ソートとして振る舞う**。case 001では volume 単独と**完全一致
（42/42）**、case 000でも41中39位置が同じ。

原因は係数の大きさではなく**3量が相関していること**:
`base_area ~ mass` が **+0.94〜0.95**、`volume ~ base_area/mass` が
+0.62〜0.79。相関した信号を固定重みで混ぜても支配項が返るだけ。

唯一ほぼ直交しているのは **density（`volume ~ density` = −0.17〜−0.24）**で、
これは順序側で一切使われていない。

`cutout_filler`（−0.05）は「隙間埋め要員を少し後ろへ」の意図だが
**41個中19個・42個中17個に発火**する。微調整ではなく半分の一括シフト。

### ストリームの構造

配布シミュレータの `item_params.xlsx` は**7型ちょうど**（スーツケース大中小、
ダッフル、段ボール、大型リュック、小型デイパック）で、寸法・質量・摩擦は
すべて固定値。変動するのは `is_prioritized` のみ。属性まで含めて完全に
交換可能なペアが **case 000で15.0%、case 001で23.2%**。

**ただしこれは公式契約ではない。** `COMPETITION_RULES.md` と
`COMPETITION_QA.md` の全文を読んだが、荷物の型数・寸法カタログを固定する
記述は**存在しない**。要項は「最終評価では暫定評価とは別の評価sceneが用いられ
る」と明記し、QAは「全課題に汎用的に動くこと」と述べている。
**7型に依存した設計は書けない。**

## 理論 — 未解決点は名指しされている

`MATHEMATICAL_MODEL.md:23` が挙げる未解決:

> 1. 実現可能な局所構造の候補族を**どう生成するか**

理論はブロック `b = (S_b, π_b, ρ_b, d_b, σ_b)`、集合パッキング制約、
充填率 `η_b`、実行意味論を定義しているが、**生成器がない**。実装は
`|S_b| = 2` で、しかもdry-run履歴から拾う**探索出力依存**の形。

### 定式化（Proposed）

`R(B) = {S : S が直方体を構成する}` は下方閉でないので単体複体ではない。
複体になるのは:

- `K_extend = {S : ∃R ∈ R(B), S ⊆ R}` — 「何かを足せば直方体にできる」集合族
- 頂点を**合法配置** `q=(b,g,v)` にした独立集合複体 `K_{W,H}`（衝突グラフの
  独立集合）。完全充填はunionが領域に等しい面 = exact cover

生成側は**接合代数**:

```
(S₁,d₁) ⊕ₐ (S₂,d₂)    d[a] = d₁[a]+d₂[a],  d[b] = max(d₁[b],d₂[b])  (b≠a)
```

これが生成するのは**ギロチン（スライス木）構造**のみ。風車型などの
非ギロチン配置は取りこぼす。

### 搬入制約が部分複体を切り出す（この問題固有）

単体複体は順序を持たないが、積み込みは逐次かつ不可逆（要項§3、QA「取り出し・
移動は不可」）。面 `F` が **loadable** であるとは、各挿入の搬入経路が既に
置いた分と干渉しない順序が存在すること。これは下方閉なので

```
K_load ⊆ K   は部分複体
```

**探索しているのは `K` ではなく `K_load`。** そしてギロチン構造は搬入順序を
構成的に与える（Y切断ごとに奥側を先）ので、`⊕ₐ` の生成物は**自動的に
`K_load` の面**になる。扱いやすさのための制限と物理制約が一致している。

`π_b` はスライス木の走査順そのもので、別途探す必要がない。

### ただし、この定式化が答える問いは起きない

**容器の有効容積 4.007 m³ に対し、荷物41個の合計体積は 2.600 m³（64.9%）。**
容器を敷き詰めるだけの荷物が存在しないので、exact coverは空集合。
「どの部分集合が直方体を構成するか」はこの実例では一度も問われない。

実際の目的は placed 最大化 = `K_load` の最大濃度の面 = 最大独立集合で、
NP困難、`|V| ≈ 10⁴`が1手ごとに作り変わる（`late-snapshots-not-starved`:
終盤27スナップショットで有効候補が数千〜3.6万）。**解かない。**

定式化が与えるのは**loadableが保証されたマクロ手の生成器**だけで、これは
解法ではなく探索圧縮の道具。しかも:

| 課題 | pool | ブロックを組めるか |
|---|---:|---|
| A | 1（offlineあり） | 可 |
| B | 3〜40 | 窓次第 |
| C | 1 | **不可**（1個ずつ届き並べ替え不可） |

**ブロックは実質Aの道具**であり、そのAの順序探索は帰無モデル以下と測定された。

`K_load` の区別（幾何的両立では足りない）だけは、ブロックを組まなくても
L1/L2に直接効く。

## 分割をタスクから階層へ移す根拠

今日1日で起きた衝突:

- `aa981cd`（trunk）と `6502561`（このbranch）が**独立に同じTask A訂正**をした
- fingerprintの偽陰性を Task C が `0a3c293` で**診断**し、こちらが `42793f8` で
  **実装**した。互いに知らないまま
- cherry-pickが2回衝突し、1回は無関係な台帳22件を巻き込みかけた

L1〜L3は3課題すべてを通るのに、branchが課題で切られているため
**同じ関数を別branchが同時に触る**。L4だけがタスク固有。

提案する分割:

- **L0/L1** — 計器と候補生成（最もレバレッジが高く、いま動いている）
- **L2** — 選択（3回の棄却を、直した計器で問い直す）
- **L3** — 配分（終盤が未着手）
- **L4** — 順序（Aのみ。現状、投資の根拠が弱い）
