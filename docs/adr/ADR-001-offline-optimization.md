# ADR-001: オフライン最適化（積付順序決定）のアルゴリズム戦略

**Status:** Accepted / Baseline Implemented  
**Amended by:** ADR-002 (§5 に1荷物あたりの作業予算を追加)、ADR-003 (§2 の共有範囲を可行性契約へ限定)  
**Date:** 2026-07-23  
**Deciders:** たろう

## Context

空港手荷物積付コンペのオフライン最適化では、最大2台のLD3コンテナに対する最大80個の手荷物について、3分以内に積付順序だけを返す。課題Aのオンライン側はプールサイズ1であり、オフライン側が選んだ順序を、オンライン配置コアが逐次処理する。

したがって順序の評価には、属性だけの代理スコアではなく、オンラインで実際に使用する配置コアのドライラン結果を使う。公式シミュレータの `get_init_states()` からは、コンテナ形状面、有効体積、棚、優先コンテナ属性を含む `container_list` が取得できることを確認済み。

## Decision

「構築的初期順序 → 共通配置コアによるドライラン → Or-opt / swap / 局所部分列テンプレート局所探索」を採用する。

### 1. 構築的初期順序

体積、最大底面積、重量を正規化した複合スコアで降順に並べる。小型・軽量で切り欠き部の隙間埋めに使いやすい手荷物は少し後ろへ送る。

現行の優先・ソフト手荷物のグループ順は維持し、局所探索も同じグループ内だけで行う。このルール自体の最適化は別ADRで扱う。

### 2. 共通配置コア

オンライン `policy()` とオフラインドライランは、同じ候補生成、幾何制約、支持判定、ランキング処理を呼び出す。オフライン専用の別配置器は作らない。

> **ADR-003 により修正済み。** 「ランキング処理」の共有は外れた。共有必須は可行性契約（inclusion・衝突・支持・orientation/anchor構成・状態遷移proxy・invalid判定）であり、候補列挙予算とranking/risk補正は目的に応じて異なり得る。現在 risk 補正はオフラインに適用されていない。

ドライランは各手荷物について次を行う。

1. 現在の仮想コンテナ状態から配置候補を生成する
2. `local_to_world`、棚実寸、3次元最近接距離による15 mm搬入余裕、公式のY→X二段搬入経路、8 cm落下開始高さ、settle後の観測クォータニオンから再構成した実AABBを含む共通制約で候補を絞る
3. オンラインと同じランキングで配置を1つ選ぶ
4. 仮想コンテナへ配置結果を追加する
5. 配置不能になった時点でエピソードを終了する

### 3. 評価順序

候補順序は次の辞書式順序で比較する。

1. 配置成功個数
2. 配置成功体積
3. 空間充填率
4. 安定性プロキシ
5. 正規化重心高さ（低い方を優先）

これにより、安定性が見栄えのよい部分解が、より多くの手荷物を配置できる解を逆転することはない。

`w1 * 充填率 + w2 * 安定性` はレポート、将来のGA選択、同格解の分析用に残す。既定値は `w1:w2 = 0.65:0.35` とし、環境変数で変更できる。ただし、このスカラー値は上記の失敗優先順位を上書きしない。

### 4. 安定性プロキシ

現在のプロキシは次の成分を0〜1へ正規化して合成する。

- 平均支持面積比: 45%
- 最小支持面積比: 20%
- 支持領域内の重心投影マージン: 20%
- 下側手荷物との重量比: 10%
- 平均支持接点数: 5%

加えて、全体重心高さ、最小支持マージン、平均・最小支持面積比を個別に保持する。ソフト手荷物と優先手荷物は、後続手荷物の支持面として扱わない。

これは振動テストの代替近似であり、物理シミュレーションとの相関は未検証である。

### 5. 局所探索と時間制御

- 近傍操作: swap、Or-opt（1個抜き取り・再挿入）、逐次実行可能な局所部分列テンプレート
- 探索開始点: 構築的初期順序
- 採択: 辞書式評価が改善した場合だけ更新
- 既定乱数シード: 固定
- キャッシュ: 評価済み順序の結果を再利用
- 探索予算: 180秒制限のうち最大150秒
- 次評価の開始判定: 直近ドライラン時間の移動平均に対し、残り時間が1.5回分未満なら新しい評価を始めない
- 最大評価回数: 既定1000回
- フォールバック: 常にその時点の最良順序。改善がなければ構築的初期順序

配置コアが遅い場合は自動的に評価回数が減るため、楽観的な固定反復回数には依存しない。

### 6. 逐次実行可能性付きマクロ

小規模ブロックを次で表す。

```text
b = (S_b, π_b, ρ_b, d_b, σ_b)
```

- `S_b`: 構成する荷物ID集合
- `π_b`: 共通配置コアで成立した内部順序
- `ρ_b`: ブロック最小隅をアンカーとする相対位置・姿勢
- `d_b`: 完成後のbounding box寸法
- `σ_b`: 内部充填率、粗い上面プロファイル、最小支持率、総質量、重心

探索器からは一つの時間拡張行動として扱う。ただし評価時には、`π_b` の各荷物を共通配置コアで先頭から逐次再生する。途中の一手でも成立しなければ、その候補順序は通常どおり配置失敗として評価する。

したがってこれは、計画上はマクロ、公式API上は部分列テンプレートである。単品近傍を置き換えず、次の近傍和として扱う。

```text
A(s) = A_single(s) ∪ A_block(s)
```

初期実装は `|S_b| = 2` に限定する。構築的初期順序を一度ドライランした実行履歴から、同じ荷物グループ・同じコンテナへ連続して配置できた2荷物を候補化する。候補は支持率、内部充填率、外形高さで順位付けし、上位8件だけ保持する。

Task1では、ブロックをまとめて前後へ移動する部分列近傍として使う。最終出力は従来どおり荷物IDの一次元順列である。

Task2のプールサイズ1では、未到着荷物を含むマクロは実行しない。ブロックの上面・支持・残余凹部は将来価値の状態特徴として扱い、仮想未来を使うrollout内部でのみTask1型マクロを再利用する。

## Dry-run Result Contract

実装は少なくとも次を返す。

- `placed_count`
- `failed_index`
- `placed_volume`
- `fill_ratio`
- `stability_proxy`
- `center_of_mass_z`
- `normalized_center_of_mass_z`
- `mean_support_ratio`
- `min_support_ratio`
- `min_support_margin`
- `mean_support_count`
- `runtime_seconds`

## Consequences

- オンライン配置とオフライン評価のずれを抑えられる
- 配置失敗を最優先で避けながら、充填率・安定性・低重心を順に改善できる
- 実行速度に応じて探索量が自動調整され、30秒の終了余裕を持てる
- 良好な2荷物の局所構造を部分列単位で移動でき、順列近傍を多尺度化できる
- マクロ候補も各評価では逐次再生されるため、公式APIの一個ずつ配置する制約を迂回しない
- 配置コアの変更はオフライン評価にも直接影響するため、共通コアの回帰テストが必要になる

## Remaining Work

1. 安定性プロキシと実際の振動テストの相関検証
2. `w1:w2` の比較実験（0.8:0.2、0.65:0.35、0.5:0.5）
3. clean / nuisance条件を含む小規模ベンチマーク
4. 評価済み順序キャッシュに加え、共有プレフィックス状態キャッシュが有効かを速度計測
5. 実コンペ環境の4vCPUで、1ドライラン時間と150秒内評価回数を計測
6. 2荷物マクロの採用率、再生失敗率、圧縮率、多様性損失をA/B計測
7. 2荷物で改善が確認できた場合だけ、保持順序数 `q=1..3` と3〜4荷物へ拡張
