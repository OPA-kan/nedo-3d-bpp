# placement / soft をローカルで数える

公式スコア 6 成分のうち、同梱シミュレータが計算するのは **2 つだけ**
(`fill_score`, `num_placed_items`)。残る cog / stability / placement / soft は
評価基盤側にしか無く、**投稿してフィードバックを読むまで一切見えなかった**。
submission22 で placement **4.45** / soft **7.65** が最悪の 2 成分だと分かったのも
それが理由である。

そのうち 2 つは規則が完全に公開されていて**物理を必要としない**。
これはその規則の転記である。

## 実装

`simulator/src/ground_handling/diagnostics.py` の
`calculate_attribute_placement()`。`Evaluator.settled_snapshot()` から呼ばれ、
`step_metrics` の各ステップに乗る。`run_risk_ablation.py` は最終ステップの値を
各 case の `attribute_placement` として出す。

### 規則(`simulator/README.md:379` の転記)

* 優先手荷物が、**属性の異なる**荷物に上から接触されていたら減点
* ソフト貨物も同様
* **同属性の積み重ねは明示的に減点なし**(優先の上の優先、ソフトの上のソフト)
* 優先手荷物用コンテナが**あるのに**一般コンテナへ置いたら減点
* **優先とソフトは独立に評価**。両方の属性を持つ荷物は 2 回судされる

## これは何を返し、何を返さないか

返すのは**違反数**と属性ごとの clean ratio。

**違反数 → 0〜100 の公式スコアへの写像は非公開なので、4.45 は再現できない。**
これは単調な代理量にすぎず、「arm A と arm B のどちらが優先/ソフト配置を
壊したか」を言うためのものである。**clean_ratio をスコアとして提示しないこと。**
ガードとして、返り値のキーに `score` を含めない単体テストを置いてある。

`clean_ratio` は該当属性の荷物が 0 個のとき **`None`**(1.0 ではない)。
ソフト貨物を含まないストリームには意見が無く、捏造した 1.0 を arm 平均に
混ぜると、実際に運んでいるエピソードが薄まるからである。

## 唯一のモデリング選択

「上からの接触」は settled PyBullet AABB から読む。B の底面が A の天面から
`CONTACT_TOLERANCE = 0.02` 以内にあり、footprint が重なっていれば「覆っている」。

接触点(`getContactPoints`)の方が忠実だが、**最後に物理を進めた時点に依存する**。
呼び出しタイミングで変わる計器は、一定方向に少しずれる計器より悪い。

代償として、薄い隙間を挟んだ覆いを見落とし、角だけ触れているものを覆いと
数えうる。**1 カウントの差はノイズとして扱うこと。**

## 初回実行で出たもの — 記録しておく

b000-k40(base)の最終状態:

```
priority_items 4, soft_items 3, has_priority_container false
priority_covered_by_other 1   <-- 優先荷物 4 個中 1 個が一般荷物の下敷き
priority_misrouted 0, soft_covered_by_other 0
priority_clean_ratio 0.75, soft_clean_ratio 1.0
```

**agent は `support_surfaces()` で優先荷物の上への配置を全面禁止しているのに、
覆いが発生している。** つまり過剰制約は目的を達成していない — 公式が許す
同属性積み重ね(体積になる)を捨てながら、違反そのものは防げていない。

機序の候補(**未検証**): `support_surfaces()` が支配するのは settled 候補の
アンカー生成だけで、**release 候補(落下配置)は覆う位置に着地しうる**。
物理の settle でずれる経路もある。ここは次に確かめる価値がある。

## 引き継ぐ注意点

1. **development 5 config には優先コンテナが存在しない**(000 も 001 も
   `is_prioritized: false` のコンテナ 1 個のみ)。したがって
   `priority_misrouted` は**この suite では常に 0** で、経路規則は
   ローカルで検証できない。評価基盤には優先コンテナのあるケースがある
   はずなので、そこは依然として盲点である。
2. soft 貨物は 41 個中 13 個(case 000)と多いので、ソフト規則の方は
   ローカルで十分に効く。
3. これは**計器であって目的関数ではない**。ランカーに入れる前に、まず
   既存の arm 比較(`first_pass64` vs 既定など)でどう動くかを見ること。
4. cog は質量と位置から計算できるが正規化が不明、stability は揺らし手順が
   非公開で最も高価。**6 成分中まだ 2 つが完全な盲点として残る。**
