# Wedge RL: findings

The chamfer of the LD3 leaves a triangular prism along one wall (0.111 m^3 in
the c1 container) that no box can stand in.  The only way to use it is a
staircase: a base on the floor at the floor line and steps that overhang the
base into the wedge as far as the inclined wall allows.  `wedge_rl` is a
small RL problem built on exactly that: a strip along the chamfer plus 0.80 m
of floor, boxes from the official seven types, candidates generated by
geometry and filtered by rule-alpha's analytic validator, PASS allowed, reward
the volume each placement puts left of the floor line.

## Runs

| run | where | what |
|---|---|---|
| `baselines-c1.json` | Actions run 34092586287 | hand rules on the evaluation seeds 20000-20039 |
| `ppo-c1-s0/` | same run | PPO, layout c1, 14 items, 32 episodes per iteration, 200 iterations in 4.3 h before the runner limit; `policy.pt` is the best checkpoint (iteration 180), `history.json` the learning curve, `eval.json` the held-out comparison |
| `replay-c1.jsonl`, `replay-c1-summary.json` | sandbox, `python -m wedge_rl replay` | the same arrangements executed in the official PyBullet simulator |

## Result

Mean strip volume on the forty held-out seeds, m^3 (wedge = 0.111):

| policy | analytic (env) | settled (PyBullet) | boxes placed | accepted |
|---|---|---|---|---|
| PPO (iter 180) | 0.0677 | 0.0680 | 5.1 | 203 / 203 |
| staircase rule | 0.0499 | 0.0490 | 6.5 | 256 / 257 |
| greedy any | 0.000 | - | 7.0 | - |
| random | 0.003 | - | 4.2 | - |

Paired on the settled figure, PPO minus staircase is +0.019 m^3 per episode
(bootstrap 95 % interval 0.011 to 0.027; 27 wins, 12 losses, 1 tie).  PPO
fills 61 % of the wedge, the hand rule 44 %.

Physics agrees with the environment.  Every PPO placement was accepted by the
official validator; settled boxes moved 1.2 mm in the plane on average, 7 mm
at most, and the settled strip volume is within 0.3 mm^3 of the plan.  The
one failure in eighty episodes is a staircase step on seed 20033 that the
transport sweep rejected; the analytic validator and the simulator disagree
on that pose by less than the tolerance the earlier agreement study measured
(false accepts 0.2 %).

## What the policy learned

The learning curve rises from 0.022 (untrained) through 0.049 at iteration 20
(the hand rule's level) to 0.064 at 90 and 0.069 at 180, still rising slowly
when the runner limit stopped it.

The difference to the hand rule is selectivity, not a new mechanism.  Both
build the same staircase (base at 0.04 m, steps at 0.28-0.31 m), and both
reach 0.21-0.22 m into the wedge on the steps that gain.  The rule places
6.5 boxes and 171 of its 257 placements gain nothing: it lays every item it
can as low as possible, which spends the floor strip on boxes that never
become a base for a step.  PPO places 5.1 boxes, only 84 of 203 without gain,
and passes on items that would block a better step later.  In other words
the policy learned which items to keep out of the strip, which is the part of
the problem a greedy rule cannot see.

## Caveats

* The environment is a strip in an otherwise empty container.  In an episode
  the boxes passed on go elsewhere, and neighbours to the right of the strip
  may constrain the base.  The PASS action makes this composable, but the
  volume figure is for the isolated strip.
* The evaluation container is c1 (no main shelf); c1s has the same chamfer
  but the shelf changes what can stand at the floor line.
* One seed, one layout.  The continuation run (dispatched from the
  iteration-180 checkpoint) and a c1s run are the next data points.

## Reproduce

```
python -m wedge_rl baselines --layout c1 --episodes 40 --seed0 20000
python -m wedge_rl train --layout c1 --iterations 400 --episodes 32 --out runs/wedge
python -m wedge_rl eval --policy reports/wedge/ppo-c1-s0 --episodes 40 --seed0 20000
python -m wedge_rl replay --policies ppo,staircase --policy reports/wedge/ppo-c1-s0 \
    --episodes 40 --seed0 20000 --out runs/replay.jsonl --summary runs/replay-summary.json
```

Long runs go through `.github/workflows/wedge-ppo.yml` (workflow_dispatch; a
run can start from a previous run's checkpoint via `init_run_id`).
