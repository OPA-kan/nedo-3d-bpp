# 反復は本当の分散を測っていない

## 観測

`base` アーム——同一コード、同一既定、ノブ設定なし——を、並列度の異なる
2つの波で比較したもの。

| 構成 | 2並列の波（42話） | 4並列の波（84話） | 波間の差 |
|---|---|---|---:|
| b000-k15 | `[19,19,19]` | `[21,21,21]` | **+2** |
| b000-k20 | `[20,23,19]` | `[21,21,18]` | −0.67 |
| b000-k40 | `[17,17,17]` | `[21,21,21]` | **+4** |
| b001-k20 | `[22,17,22]` | `[19,16,21]` | −1.67 |
| b001-k30 | `[19,19,19]` | `[17,17,17]` | **−2** |
| c000-k1 | `[23,23,23]` | `[18,22,19]` | **−4** |
| c001-k1 | `[21,21,21]` | `[21,21,16]` | −1.33 |

**波の中では3反復がしばしばビット同一**（分散ゼロ）、**波の間では最大4動く。**

## 機序

エージェントは壁時計締切で動く（`POLICY_BUDGET_SECONDS=6.5`）。1つの波の
中では全エピソードが同じ負荷パターンを見るので、時間予算探索は同じ basin に
落ち、反復は決定論的になる。並列度が変われば1エピソードあたりのCPUが変わり、
**アーム全体が移動する**。

## 何が壊れるか

`reports/benchmarks/baseline.json` の
`minimum_resolvable_placed.paired_3v3_same_run` は**波内**のばらつきから
導かれている。**b000-k40 の床は 3.93 で、その base アームは波間で 4.00
動いた。** 負荷差だけで、実効果を雑音から分離するはずの床を越える。

## 何が生き残るか

**同一run内のペアA/Bは有効**である。両アームが同じ負荷を見るので、その波の
負荷条件のもとでの差は測れている。無効なのは:

* **同一アームの波をまたいだ比較。** `attr_support_rule` が2波で placed と
  shake の両方で符号を反転させたのはこれである。
* **4 placed 程度の効果に基づく採否。** 並列度の変更と区別できない。

## 本セッションが継承する交絡

並列度を波ごとに変えてしまっている:

| 波 | 並列度 |
|---|---|
| post-shake-revalidation | 直列 |
| post-shake-direct | 2並列 |
| soft-stack-shadow | 直列 |
| soft-generation | 直列 |
| attribute-support | 2並列 |
| attribute-contract | 4並列 |

同一run内の裁定（属性契約の4ゲートなど）は影響を受けないが、**波をまたいで
読んだ数字はすべてこの交絡を含む。**

## 直し方

1. **線ごとに並列度を固定**し、波のメタデータに記録する。
2. **床を波間の base 反復から導き直す。** 波内反復はビット同一になりうるので
   分解能を過大評価する。
3. それが揃うまで、**4 placed 程度の効果に依拠した採用をしない。**
